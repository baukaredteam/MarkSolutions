# W0-02 Implementation Plan — Prisma Deterministic Bootstrap

**Goal:** Make `db:generate`, migration validation, and full test suite reproducible from a clean checkout. Production target: PostgreSQL 16. No mock adapters, no file KMS, no local storage in production/stage.

**Constraints from W0-02_PRECHECK.md:**

- 25 historical SQLite migrations are NOT PostgreSQL-compatible as-is
- No production data confirmed in repository
- PrismaService uses PrismaLibSQL adapter (must be removed for PG)
- Test suite mutates DATABASE_URL per spec, runs `prisma migrate deploy` against file: DB
- No CI pipeline exists
- `fileParallelism: false` (sequential test execution)

---

## Preferred Design: PostgreSQL Baseline + Dual-Mode Development

### Strategy

Since historical SQLite migrations cannot be applied to PostgreSQL (different DDL semantics, data backfill in w5_tyyn_money), create a **new PG baseline migration** that recreates the full schema from `schema.prisma`. Archive old SQLite migrations into a `packages/db/prisma/migrations/_archived_sqlite/` directory (not deleted — git history preserves them).

Keep `schema.prisma` provider as `sqlite` for local development (per ADR-015: SQLite dev, PostgreSQL prod). Production/stage use `DATABASE_URL=postgresql://...` and the test/bootstrap infrastructure creates a disposable PostgreSQL database. The key insight: **Prisma allows the schema provider to be "sqlite" while still connecting to PostgreSQL** — but `prisma migrate deploy` requires provider match. Therefore, the solution is:

1. **For development (`migrate dev`):** Keep SQLite. `prisma migrate dev` works with `provider = "sqlite"`. This is the primary dev workflow.
2. **For production/stage (`migrate deploy`):** Use a PG baseline. Switch `provider = "postgresql"` at deploy time (or maintain a parallel `schema.pg.prisma`), and apply the baseline migration.
3. **For tests:** Use a disposable PostgreSQL database per spec (or per test run), applying the PG baseline.

### Decision point: single schema vs dual schema

**Option A (Recommended): Single schema, provider switch at deploy time**

Maintain one `schema.prisma` with `provider = "sqlite"`. For PG operations:

- Create a `packages/db/prisma/schema.pg.prisma` that is identical except `provider = "postgresql"` and points to a different `DATABASE_URL` env var.
- `db:generate:pg` runs `prisma generate --schema schema.pg.prisma`
- `db:migrate:pg` runs `prisma migrate deploy --schema schema.pg.prisma`
- `migration_lock.toml` stays as `sqlite` for the SQLite workflow; PG workflow has its own lock file under `schema.pg.prisma`'s migration directory.

**Option B (Fallback): Single schema, runtime provider override**

Use a single `schema.prisma` with a conditional provider via a build-time script that generates a temporary `schema.pg.prisma` from the same model definitions. This avoids maintaining two schema files but adds build complexity.

**Recommendation:** Option A. Two schema files is explicit, auditable, and avoids build-step magic. The model definitions are the same; only the datasource block differs.

### Migration strategy

| Scenario                             | Action                                                                                                                                         |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| New deployment (no existing PG data) | `prisma migrate deploy --schema schema.pg.prisma` applies baseline. Clean.                                                                     |
| Existing SQLite data → PG            | **Rebaseline:** pg_dump from SQLite → pg_restore to PG, OR data migration script. Owner decision required if any instance has production data. |
| Schema change (new model/field)      | `prisma migrate dev --schema schema.pg.prisma` on disposable PG → commit new migration SQL in `migrations_pg/`.                                |
| Rollback (forward-fix)               | Create a new down-migration in `migrations_pg/`. Never edit committed migrations.                                                              |

### Test strategy

| Test type                          | Bootstrap method                                      | DB                                              |
| ---------------------------------- | ----------------------------------------------------- | ----------------------------------------------- |
| Unit tests (packages/)             | Vitest (no DB needed)                                 | N/A                                             |
| Integration tests (apps/api/test/) | `TEST_DATABASE_URL` → disposable PG schema (per spec) | `markflow_test_<random>`                        |
| E2E browser tests                  | Full app stack with SQLite dev.db                     | SQLite (unchanged)                              |
| CI (future)                        | `scripts/bootstrap.sh` on fresh runner                | SQLite for unit/integration; optional PG matrix |

### Risks

| Risk                                               | Mitigation                                                                                                                          |
| -------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| Dual schema drift                                  | Single source of truth: models in `schema.prisma` are copied to `schema.pg.prisma` via a build step; add CI check that models match |
| Test bootstrap time on PG                          | Each spec creates its own schema via `CREATE SCHEMA` + migrate; parallelizable with `fileParallelism: true` in future               |
| Seed data inconsistency between SQLite and PG      | Seed is idempotent; same seed works on both providers if types are compatible (JSON, BigInt, etc.)                                  |
| w5_tyyn_money backfill migration in SQLite history | Archived; PG baseline starts fresh with correct money values                                                                        |
| No CI pipeline                                     | W0-06 adds CI; W0-02 adds the scripts that CI will call                                                                             |

## Rollback / Forward-fix

**Rollback:** Remove `schema.pg.prisma`, `migrations_pg/`, and PG-specific scripts from `package.json`. Restore old migration lock. Zero code impact — pure infrastructure files.

**Forward-fix (if migration fails on PG):** Create a new down-migration in `migrations_pg/` that fixes the issue. Never amend committed migrations.

**Data safety:** No production data exists in the repository (confirmed in W0-02_PRECHECK.md). If owner confirms no production instance has data, SQLite migrations can be archived without recovery concerns.

## Blockers / owner decisions

1. **Production data existence:** Is there any production data on any live MarkFlow instance? If yes, migration strategy needs pg_dump/pg_restore coordination. If no, SQLite migrations can be archived. **Owner: product owner / deployment lead.**

2. **PG baseline scope:** Should the PG baseline include ALL models (including future W1-W6 models not yet implemented)? Recommendation: baseline covers only current models (W0 scope); future models added via `prisma migrate dev --schema schema.pg.prisma`.

3. **CI timeline:** W0-06 adds CI. Should W0-02 include a minimal GitHub Actions workflow for validation gates, or leave CI entirely to W0-06? Recommendation: W0-02 adds the `scripts/` commands; W0-06 wires them into a workflow.

4. **Dev mode retention:** Keep SQLite as the primary dev workflow (fast, no Docker needed per ADR-015). PG is for test validation and production deployment. Confirm this dual-mode approach is acceptable.
