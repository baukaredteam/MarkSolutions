## 2. Create order UI `/order/create` (2 шага)

Путь в кабинете: `/order/create`. Два шага, затем «Создать заказ». Wire: единственный mutating-метод заказа — `POST /api/orders` (`MARKING-CODE-ORDER.CREATE`) из CONTRACT. Этот документ **не** авторизует вызов.

### Шаг 1 — Общие

| UI поле | Обязательность в ЛК | Наблюдение 2026-09-03 | Wire (`POST /api/orders`) |
| --- | --- | --- | --- |
| Эмитент | fixed (не редактируется) | Текущий УОТ кабинета | Нет отдельного поля; эмитент = authenticated party |
| Товарная группа | да | Сначала выбирается группа; от неё зависят следующие поля | `productGroup` (string, обяз.) → `autofluids` |
| Место осуществления деятельности (МОД) | да | Список площадок участника | `businessPlaceId` → **`803`** (int32; CONTRACT ловушка 5) |
| Цель маркировки | да, **после** выбора группы | **Первичная** / **Повторная** | **UI vs wire:** wire `releaseMethodType` = `PRIMARY` \| `REMAINS` \| `COMISSION` \| `REMARK`. UI показала 2 значения. Первичная ≈ `PRIMARY` (офиц. «первоначальная маркировка»). **Не выдумывать**, что Повторная = `REMAINS` или `REMARK` |
| Номер производственного заказа | optional | Свободный текст | Офиц. таблица: `poNumber` (нет). CONTRACT one-liner это поле не перечисляет — **UI vs CONTRACT-summary**, не новый метод |

Кнопка шага: **Далее**.

**UI vs wire (`releaseMethodType`):** на **этой** форме цель маркировки — радио Первичная/Повторная. Отдельный фильтр «release-method» есть на **странице кодов**, не явно на `/order/create`. Не изобретать пятый enum и не слать категорию вместо `releaseMethodType`. CONTRACT по-прежнему требует `releaseMethodType` на POST; текущий MarkFlow `createOrder` это поле **не** шлёт (follow-up, не этот PR).

### Шаг 2 — Товары

| UI поле | Когда появляется | Наблюдение 2026-09-03 | Wire |
| --- | --- | --- | --- |
| GTIN | сразу | **Ровно 14 символов.** `4650063110374` (13 цифр) — reject. `04650063110374` принимается форматом, lookup: «Описание товара с таким GTIN не найдено», пока карточка не **опубликована** | `products[].gtin` (string, обяз.). Офиц. GET кодов: GTIN — 14 цифр, слева нули |
| Наименование | после резолва карточки | auto-fill из описания товара | Нет в теле заказа |
| Тип упаковки | после резолва карточки | auto-fill из карточки (пример: «Единица товара») | `products[].cisType` = `UNIT` \| `GROUP` \| `SET`. «Единица товара» ≈ `UNIT`. На форме не свободный ввод до резолва GTIN |
| Серийники | радио **disabled**, пока GTIN не резолвится | **OPERATOR** / «Автоматически» vs **SELF_MADE** | `products[].serialNumberType` `OPERATOR` \| `SELF_MADE`. `serialNumbers[]` только при `SELF_MADE` (офиц. таблица) |
| Quantity | **только** после валидного GTIN (карточка найдена) | Иначе поля нет | `products[].quantity` int32, обяз. на wire |

Финальная кнопка: **Создать заказ**.

### GTIN-14 (правило для MarkFlow, без новой checksum-формулы)

| Ввод | STAGE ЛК | Что делать в MarkFlow |
| --- | --- | --- |
| 13 цифр, напр. `4650063110374` | Reject: не 14 символов | Принять 13, **дополнить слева до 14** (`04650063110374`). Check-digit — существующее правило репо (`GtinResolver` / GS1 mod10 в `CATALOG-MM` / ADR), **не изобретать** алгоритм в этом файле |
| 14 цифр, карточки нет / не опубликована | Lookup fail: «Описание товара с таким GTIN не найдено» | Блокировать createOrder (см. §4) |
| 14 цифр, карточка **Опубликованные** | Наименование + тип упаковки auto-fill; quantity и serial radios оживают | Можно собирать тело `POST /api/orders` (после отдельного «да» человека) |

Не выдумывать отдельный STAGE endpoint «lookup GTIN». Наблюдение — поведение UI, не новый метод CONTRACT.

## 3. Карточка «Описания товаров» (модерация)

Карточка **должна существовать** и быть в статусе **Опубликованные**, иначе шаг 2 заказа не резолвит GTIN.

В UI **нет** прямой кнопки «Опубликовать». Есть **«Отправить на модерацию»**.

### Поля spreadsheet, увиденные в ЛК

| UI / колонка | Пример 2026-09-03 | Заметка |
| --- | --- | --- |
| ТГ | «Смазочные материалы и специальные жидкости» | wire group `autofluids` |
| Категория | моторные / компрессорные масла | `category_autofluids_motor` — не `productGroup` |
| ТН ВЭД | `2710198200` | В перечне `docs/CATALOG-MM.md` |
| GTIN | `04650063110374` | GTIN-14 |
| Тип упаковки | Единица товара | ≈ `cisType=UNIT` |
| Торговое имя RU / KZ | (заполнено) | Двуязычное имя |
| Бренд | Gazpromneft | |
| Страна | Россия | |
| КП ВЭД | `20.59.41` | Есть в справочнике CATALOG-MM |
| GCP | `465006311` | Префикс GS1 |
| Фото | **Лицевая + Обратная** обязательны | ≥2 фото; совпадает с CATALOG-MM атрибут 32 |
| GS1 prefixes в кабинете | **пустые** | Не считать префиксы «уже подтянутыми» из ЛК |

### Пример отправленной карточки (не считать опубликованной)

| Поле | Значение |
| --- | --- |
| GTIN | `04650063110374` |
| id | `e69b4f24-6e9f-44f5-9dc3-b7bf8a5ebc45` |
| Статус | **На модерации** |

Пока статус не **Опубликованные**, createOrder lookup в ЛК не находит описание. Это **гейт модерации**, не новый API.

Не выдумывать ИС МПТ endpoint publish/moderate. Машина MarkFlow CAT (`Draft→…→Registered`, CAT-013) — внутренняя; статус «Опубликованные» в ЛК ИС МПТ — внешний факт кабинета.
