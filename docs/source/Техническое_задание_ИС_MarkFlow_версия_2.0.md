# Статус документа и правила применения

Настоящий документ является расширенным техническим заданием на разработку ИС MarkFlow. Он может использоваться как приложение к договору после заполнения полей, отмеченных «Подлежит уточнению», получения официальных спецификаций внешних систем и согласования расчетных нагрузок. Любое расхождение между данным ТЗ и официальной документацией внешней системы разрешается в пользу официальной документации, действующей на дату реализации конкретной интеграции.

Все числовые показатели производительности и SLA, помеченные как рекомендуемые, должны быть подтверждены нагрузочным обследованием до фиксации цены и сроков. Детали API ИС МПТ, GS1, НКТ, 1ecom.kz, банков, ЭДО и иных систем не выдумываются разработчиком и вносятся в паспорта интеграций только на основании выданной документации и тестового доступа.

# Оглавление

# 1. Общие сведения

## 1.1. Наименование системы

Полное наименование: информационная система автоматизации маркировки и прослеживаемости товаров «MarkFlow».

Краткое наименование: ИС MarkFlow.

Правообладатель и оператор коммерческой платформы: ТОО «Mark Solutions» либо иное юридическое лицо, определенное Заказчиком.

## 1.2. Основание для разработки

Основанием служит исходная процессная схема, в которой предусмотрены: регистрация продавца через кабинет 1ecom.kz; создание идентификатора продавца и лицевого счета; изолированное хранение данных клиентов; выбор товарной группы; создание и проверка карточек; получение GTIN и НТИН; пополнение баланса; заказ и получение кодов маркировки; формирование этикеток; печать и нанесение; отчет о нанесении; складская приемка; уведомление о ввозе; акт приема-передачи и смена статусов кодов.

## 1.3. Назначение документа

Документ фиксирует функциональные, интеграционные, информационные, архитектурные, эксплуатационные и приемочные требования, достаточные для проектирования, оценки, разработки, тестирования, внедрения и сопровождения системы.

# 2. Цели, принципы и ожидаемые эффекты

## 2.1. Цели проекта

- Создать единое цифровое окно для организаций, которым необходимо выполнять операции маркировки и прослеживаемости.
- Автоматизировать жизненный цикл от регистрации организации и товара до заказа, нанесения, движения и выбытия кодов.
- Сократить ручной ввод, количество дублирующих операций и ошибок интеграции.
- Обеспечить прозрачный финансовый учет услуг и кодов маркировки.
- Обеспечить промышленный уровень безопасности, аудита, наблюдаемости и отказоустойчивости.
- Создать платформу, расширяемую на новые товарные группы, склады, клиентов и внешние системы.

## 2.2. Ключевые показатели результата

| **Показатель**                                                 | **Целевое значение для пилота** | **Целевое значение для промышленной эксплуатации** |
| -------------------------------------------------------------- | ------------------------------- | -------------------------------------------------- |
| Доля операций, выполняемых без ручного вмешательства оператора | не менее 70%                    | не менее 90%                                       |
| Доля запросов без технической ошибки MarkFlow                  | не менее 98%                    | не менее 99,5%                                     |
| Доступность прикладного контура                                | 99,0%                           | не менее 99,5%, кроме согласованных работ          |
| Время открытия основных экранов, p95                           | до 4 сек.                       | до 3 сек.                                          |
| Трассируемость критичных операций                              | 100%                            | 100%                                               |
| Повторное создание операции при повторном запросе              | 0 случаев                       | 0 случаев при корректном Idempotency-Key           |
| Восстановление из резервной копии                              | проверяется до пилота           | не реже 1 раза в квартал                           |

## 2.3. Архитектурные принципы

- API-first и contract-first для внешних и внутренних интерфейсов.
- Идемпотентность всех финансовых, кодовых и документных операций.
- Асинхронная обработка длительных операций через брокер сообщений.
- Принцип минимальных привилегий и разделение полномочий.
- Наблюдаемость: метрики, структурированные логи, трассировка и бизнес-события.
- Конфигурационное подключение товарных групп и правил валидации.
- Неизменяемый аудит критичных действий.
- Защита кодов маркировки как конфиденциального цифрового актива.

# 3. Объем и границы проекта

## 3.1. Входит в базовый объем

- Регистрация и верификация организаций и пользователей.
- Личный кабинет клиента, оператора, администратора, склада и поддержки.
- Товарный каталог, карточки товаров, GTIN и НТИН.
- Лицевые счета, платежи, резервы, списания, возвраты и сверка.
- Заказ, получение, защищенное хранение и выдача КМ.
- Конструктор этикеток, локальная и серверная печать.
- Нанесение, агрегация, разагрегация, переупаковка, брак и перемаркировка.
- Уведомления о ввозе, документы движения и акты приема-передачи.
- Интеграционный шлюз, API, webhooks, файловый обмен и очереди.
- Аудит, мониторинг, отчеты, уведомления, поддержка и SLA.

## 3.2. Не входит без отдельного соглашения

- Полноценная бухгалтерская система или замена ERP клиента.
- Производство и поставка принтеров, сканеров, аппликаторов и расходных материалов.
- Юридически значимый ЭДО без подключения сертифицированного провайдера.
- Изменение государственных или внешних информационных систем.
- Разработка функций товарной группы при отсутствии утвержденных правил и API.
- Миграция неструктурированных исторических данных неизвестного качества.

## 3.3. Допущения и зависимости

Для первого промышленного релиза рекомендуется модульный монолит с четкими доменными границами, отдельным брокером сообщений, объектным хранилищем и API Gateway. # 10. Интеграционная архитектура

## 10.1. Общие требования к API

- REST/JSON для команд и запросов; события через брокер; файлы — только при отсутствии API.
- OpenAPI 3.x, версия интерфейса, примеры и контрактные тесты.
- OAuth2/OIDC, mTLS, ЭЦП или иной механизм согласно внешней системе.
- Correlation-ID, Request-ID и Idempotency-Key обязательны для изменяющих операций.
- Единый формат ошибок: code, message, details, fieldErrors, correlationId, retryable.
- Rate limiting, квоты, pagination, сортировка и фильтры.
- Webhook подписывается, имеет timestamp, защиту от replay и повторную доставку.
- Payload большого объема передается через защищенное объектное хранилище с короткоживущей ссылкой.

## 10.2. Надежность интеграций

| **Механизм**    | **Требование**                                                                                     |
| --------------- | -------------------------------------------------------------------------------------------------- |
| Timeout         | Отдельные connect/read/write timeout; бесконечное ожидание запрещено.                              |
| Retry           | Только для временных и идемпотентных ошибок; exponential backoff + jitter.                         |
| Circuit breaker | Открывает цепь при превышении порога ошибок, защищает внешнюю и внутреннюю систему.                |
| DLQ             | Сообщение после исчерпания попыток с причиной, payload-ссылкой и инструментом повторной обработки. |
| Outbox          | Бизнес-транзакция и событие фиксируются атомарно.                                                  |
| Inbox/Dedup     | Входящие события дедуплицируются по message_id/event_id.                                           |
| Reconciliation  | Периодическая сверка незавершенных операций с внешней системой.                                    |
| Schema registry | Версии событий совместимы назад либо проходят управляемую миграцию.                                |
